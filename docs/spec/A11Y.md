# Accessibility (WCAG 2.2 AA) checking

Accessibility is a hard constraint for this project: every result renders as headline
text + an accessible `<table>` alongside the charts, the layout carries a skip link and
landmark structure, and forms wire `aria-invalid` / `aria-describedby`. This doc covers
how to check it.

**The bar is WCAG 2.2 AA, mobile included** (raised from 2.1 AA on 2026-08-22 for the
public-release blocker, board card 0012). Only one 2.2 AA criterion is checkable by an
off-the-shelf linter: 2.5.8 Target Size, which axe implements as `target-size`. Pa11y's
`standard` option tops out at WCAG 2.1, so `.pa11yci.json` now sets **no** `standard` and
lets axe run its full default rule set, which is a superset that includes `target-size`.

## The five criteria no linter covers

The other five 2.2 AA criteria have to be argued from the code or measured directly. Where
each stands, so nobody re-derives it:

| Criterion | Status | Evidence |
|-----------|--------|----------|
| **2.4.11** Focus Not Obscured (Min) | **checked, and it was failing** | The assistant is a `position: fixed` panel — a 24rem column on desktop, the whole screen on a phone — and the page behind it stayed in the tab order. `npm run a11y:focus` (below) measured three focus stops entirely hidden underneath it. Fixed by `resources/js/assistant-inert.js`, which makes everything outside the panel `inert` while it is open; the same command is the standing check. |
| **2.5.7** Dragging Movements | **met** | The only drag-operated controls are five native `<input type="range">` sliders (results what-if, threshold explorer). Native slider dragging is user-agent behaviour the author has not modified, which is the criterion's own exception, and clicking the track is a single-pointer alternative. There is no custom drag handler anywhere in `resources/js`. |
| **3.2.6** Consistent Help | **met** | The help mechanisms (MoneyHelper, Pension Wise, "How this tool works") are in the shared `components/layouts/app.blade.php` footer, so every page carries the same ones in the same relative order. |
| **3.3.7** Redundant Entry | **met** | The builder is a multi-step wizard but a **single** Livewire component: `$step` only chooses which section renders, all values stay bound, and `loadState()` restores them. The one re-entry is the password on `/user/confirm-password`, which is the criterion's security exception. |
| **3.3.8** Accessible Authentication (Min) | **met** | No CAPTCHA, puzzle or memory test exists in the app. Every credential field carries the `autocomplete` a password manager needs (`username`, `current-password`, `new-password`, `one-time-code`) and nothing blocks paste, so no cognitive function test is imposed. 2FA offers a recovery code as an alternative to the device. |

**Still needing a person at a browser** (this is what card 0001 covers): the ApexCharts canvases,
reflow and 400% zoom, a real screen-reader pass, and the judgement calls no tool makes — link
text in context, meaningful sequence, and anything conveyed by colour inside a chart.

## The authoritative check: axe DevTools / Lighthouse in your browser

For the go-live verification pass, run **current axe in the Chrome you already have** — it
is trustworthy, needs no downloads, and covers the authenticated forecast pages trivially
(just log in first):

- **axe DevTools** (free Deque browser extension): open a page, DevTools → *axe DevTools* →
  *Scan all of my page*. Do this for the landing + auth screens, then log in (the seeded
  `demo@example.com` / `password`) and scan `/dashboard`, `/scenarios/create`, a results
  page, `/account/security`.
- **Lighthouse** (built into Chrome DevTools): DevTools → *Lighthouse* → tick *Accessibility*
  → *Analyze*.

Fix the markup the report points at, not the report.

## Automated sweep (Pa11y CI)

[`.pa11yci.json`](../../.pa11yci.json) drives [Pa11y CI](https://github.com/pa11y/pa11y-ci)
(axe runner, full default rule set) over the public pages + `/welcome`, at a desktop and a
375x667 phone viewport, with `npm run a11y`, and
[`.github/workflows/a11y.yml`](../../.github/workflows/a11y.yml) runs it on push/PR.

**The headless browser must be installed explicitly.** `.npmrc` sets `ignore-scripts=true`
(a deliberate supply-chain hardening), so `npm ci` / `npm install` never runs puppeteer's
postinstall and **no browser is downloaded — locally or in CI** (an earlier note here wrongly
assumed CI would download one; it does not). The workflow installs one with `npx puppeteer
browsers install chrome` after `npm ci`, and puppeteer finds it in its cache automatically. To
run the sweep locally, either do the same, or point Pa11y at your installed Chrome:
```powershell
$env:PUPPETEER_EXECUTABLE_PATH = "C:\Program Files\Google\Chrome\Application\chrome.exe"
php artisan db:seed --class="Database\Seeders\DemoScenarioSeeder"   # demo@example.com / password
php artisan tinker --execute="App\Models\User::where('email','demo@example.com')->update(['disclaimer_acknowledged_at' => null]);"  # so /welcome renders
php artisan serve            # in one shell
npm run a11y                 # in another
```
(Herd already serves the app at `https://retireforecast.test`, but `.pa11yci.json` targets
`127.0.0.1:8000` so CI works, so the local sweep needs that `php artisan serve` or a one-off
URL override. For everything except the scripted Pa11y sweep, just use `retireforecast.test`.)

Pa11y CI is a coarse regression smoke; **axe DevTools (current axe) in the browser remains the
authoritative check** — it covers the authenticated forecast pages and the chart canvases Pa11y
does not. The `/welcome` URL logs in as the demo user to scan the first-run disclaimer page,
which only renders for a user who has **not** yet accepted it. The demo seeder marks it accepted
(`DemoScenarioSeeder`), so the sweep first resets `disclaimer_acknowledged_at` to null (the CI
workflow does this; do the same locally, as above). Otherwise `/welcome` redirects away and that
one URL times out.

## Automated sweep of the signed-in pages (`npm run a11y:auth`)

[`scripts/a11y-authenticated.mjs`](../../scripts/a11y-authenticated.mjs) logs in and runs the
same current axe over `/dashboard`, `/scenarios/create`, a scenario's edit / results / compare /
afford pages, and `/account/security`, at both viewports. Asking for the secured page bounces
through Fortify's password-confirmation screen, so the script scans that on the way past too —
nothing else reaches it. `/account/security` is then swept in **all three** of its states: the
script clicks Turn on, scans the enrolment panel, reads the setup key off the page, computes the
authenticator code itself (fifteen lines of node's own `crypto`, no dependency), confirms, scans
the enabled panel with its recovery-code list, and turns 2FA back off. That last step is what
makes the sweep safe to re-run. It is **not wired into CI** yet: the CI fixture
nulls the demo user's disclaimer so `/welcome` renders, which would bounce every signed-in
URL back to `/welcome`, and the scenario id is not fixed by the seeder. Wiring it in needs a
second seeded user and a known scenario id.

Three things this script does that Pa11y CI does not, and all three matter:

- **It checks it is on the page it is about to call green.** Pa11y drives one URL per run so it
  cannot drift; this script walks a session, and a session can be lost. It was: the
  password-confirmation step clicked a bare `button[type=submit]`, and on that page the signed-in
  layout's **Log out** button comes first in the DOM, so the sweep signed itself out and then
  reported the landing page as `/account/security` and the login page as every mobile URL, all
  green. `scan()` now compares `location.pathname` with the path it was asked for and fails the
  run on a mismatch, because a scan of the wrong page reads as coverage.
- It waits for the network to go idle **and then pauses**, because scanning a Livewire results
  page too early reports a page-wide wall of contrast "failures" that are really a transient
  loading overlay. A run that reports hundreds of contrast errors on `/results` is that
  artefact, not the page.
- It prints axe's `failureSummary`, so every contrast finding comes with its measured ratio
  and the two colours. Fix the ones under 4.5:1; do not take the bare rule name on trust.

```powershell
php artisan db:seed --class="Database\Seeders\DemoScenarioSeeder"
php artisan serve --port=8000                                       # one shell
$env:PUPPETEER_EXECUTABLE_PATH = "C:\Program Files\Google\Chrome\Application\chrome.exe"
npm run a11y:auth -- --base=http://127.0.0.1:8000 --scenario=1      # another
```

## Focus-not-obscured check (`npm run a11y:focus`)

[`scripts/a11y-focus-obscured.mjs`](../../scripts/a11y-focus-obscured.mjs) is the one 2.2
criterion worth automating ourselves, because the app has a fixed overlay: it opens the
assistant on a results page, tabs through every focus stop, and asks the document what
actually paints over each one. A stop counts as a failure only when **nothing** of it is
visible — partial cover passes at AA. It then closes the panel and asserts nothing was left
`inert` and focus went back to the edge tab, since a stuck `inert` would freeze the page.

```powershell
$env:PUPPETEER_EXECUTABLE_PATH = "C:\Program Files\Google\Chrome\Application\chrome.exe"
npm run a11y:focus -- --base=http://127.0.0.1:8000 --scenario=1
```

It needs `ASSISTANT_ENABLED=true`; with the assistant off it prints `skip` rather than a
false pass.

## Extending the automated coverage

Every page state a script can reach is now swept. What is left is what a machine cannot judge:
the rendered ApexCharts canvases always need a manual real-browser pass (only the accessible
tables and text are machine-checkable), along with reflow at 400% zoom, a screen-reader
walkthrough, link text read in context, and anything a chart conveys by colour alone.
